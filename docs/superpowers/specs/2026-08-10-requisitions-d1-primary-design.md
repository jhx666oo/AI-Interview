# 需求管理 D1 主数据源设计

## 背景

需求管理列表和详情接口目前先调用飞书多维表格，再用 D1 补充字段。飞书凭证缺失或网络异常时，页面直接返回 500；而本地镜像已经有完整的 `job_requisitions` 数据。新增和编辑虽然已经先写 D1，但删除仍只删除飞书记录。

## 目标

- 需求管理列表、详情、创建、编辑、删除在飞书不可用时仍可正常工作。
- D1 `job_requisitions` 作为页面的唯一主数据源。
- “飞书导入”继续保留，作为用户主动触发的同步入口。
- 不改变现有接口路径、筛选参数和前端字段结构。
- 不在本次改造中自动把 D1 变更推送到飞书，避免隐式外部副作用。

## 方案

### 读取

`GET /api/requisitions` 直接查询 D1，使用 `status`、`department`、`responsible_person` 参数过滤，并将 JSON 字段（城市、硬性要求、个性化需求）转换为前端数组/对象。`GET /api/requisitions/:id` 按 `id` 或 `feishu_record_id` 查询同一张表。

### 写入

保留现有 D1 写入逻辑，但移除创建和编辑请求中的自动飞书写入。创建返回 D1 记录；编辑返回更新后的 D1 记录；删除同时删除 D1 记录。保留 `feishu_record_id` 字段以便后续显式导入时去重。

### 同步

`POST /api/requisitions/sync-from-feishu` 不变，仍从飞书读取并写入 D1。页面上的“飞书导入”按钮继续调用该接口；同步失败只影响导入动作，不影响需求管理页面的日常使用。

### 兼容性

- 前端仍接收数组，现有列表、筛选、编辑弹窗无需改接口契约。
- 非管理员继续按 `responsible_person` 过滤。
- 对历史空值和非 JSON 字段使用安全默认值，不让单条脏数据阻断整页。

## 验证

1. 单元测试覆盖 D1 行转换、JSON 字段解析和筛选。
2. 本地无飞书凭证时，需求列表返回 200 且包含镜像数据。
3. 详情、创建、编辑、删除均只影响 D1。
4. 飞书导入按钮接口仍可单独调用，并且失败时不影响列表读取。
