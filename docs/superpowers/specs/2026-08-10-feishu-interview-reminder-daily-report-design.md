# 飞书面试提醒与招聘日报卡片优化设计

## 1. 背景与目标

当前系统已经能够从“面试管理”页面向面试官发送飞书卡片，也能够生成并发送招聘日报，但存在以下问题：

- 面试提醒依赖前端临时传入少量字段，缺少学历、年龄、性别和 AI 建议。
- 手动提醒发送失败时会降级为其他用户或机器人，不符合“必须由当前操作者本人发送”的业务要求。
- 简历 PDF 没有随提醒送达面试官。
- 招聘日报只有全局数字和较长的 AI 文本，无法直观看到三位负责人的当日进展。
- 手动日报与定时日报使用两套统计和卡片逻辑，容易出现口径不一致。
- 日报详情实时查询当前数据，历史日报可能随着后续业务数据变化而漂移。

本次改造目标：

1. 保留“面试管理 → 提醒面试官”入口，用当前登录用户的飞书身份发送完整候选人卡片。
2. 卡片后连续发送候选人的原始 PDF 文件。
3. 将招聘日报改造成何雨菱、杜雁玲、魏秋柠三行负责人表格，并附简短 AI 分析。
4. 统一手动发送和定时发送的数据聚合与卡片生成逻辑。
5. 先在独立分支和本地环境完成，不直接修改生产环境。

## 2. 范围

### 2.1 本次包含

- 面试提醒的数据查询、字段归一化、卡片构建、严格用户身份发送。
- PDF 从 `RESUMES_KV`/兼容 D1 缓存读取、上传飞书 IM 文件资源、发送文件消息。
- 面试提醒前端的完整成功、部分成功和失败反馈。
- 招聘日报按负责人聚合、快照保存、飞书表格卡片、短 AI 分析。
- 手动日报和定时日报复用相同的统计及展示函数。
- 单元测试、Worker 集成测试、前端构建和本地接口验证。

### 2.2 本次不包含

- 不改变简历上传、解析、AI 初筛和面试安排流程。
- 不改变现有面试官配置页面的交互。
- 不给定时批量“待审核提醒”自动附带所有 PDF；本次 PDF 只跟随人工点击的单候选人提醒。
- 不部署生产环境；生产发布需要另行明确确认。

## 3. 方案比较与选择

### 3.1 面试提醒附件方案

#### 方案 A：动态 JSON 卡片 + 紧随其后的 PDF 文件消息（采用）

- Worker 动态构建卡片。
- Worker 通过飞书 `im/v1/files` 上传 PDF，取得 `file_key`。
- 卡片发送成功后，向同一面试官发送 `msg_type=file` 文件消息。

优点：是真实可下载附件；不依赖系统登录；现有架构改动集中。缺点：飞书中视觉上是连续两条消息，而非把二进制文件嵌入单张卡片。

#### 方案 B：卡片中提供系统下载按钮

优点：实现简单。缺点：不是飞书附件；链接需要登录或短期签名；转发后权限体验较差。

#### 方案 C：使用 CardKit 模板和变量

优点：可在飞书搭建工具中可视化维护。缺点：增加模板发布和版本管理；对当前两张固定卡片收益有限。

### 3.2 日报表格方案

采用飞书原生表格组件。三位负责人固定三行，追加一行合计。未分配数据不混入任何负责人，以警告信息单独显示。

## 4. 面试提醒设计

### 4.1 入口与发送身份

入口保持 `POST /api/interviews/:id/notify-interviewer`。

该接口改用严格发送模式：

- 只允许当前登录用户自己的有效 `user_access_token`。
- token 过期时允许使用当前用户自己的 refresh token 刷新后重试一次。
- 不允许降级到数据库中其他用户的 token。
- 不允许降级到 bot token。
- 用户没有绑定飞书或重新授权失败时，返回明确的 `need_feishu_auth: true`。

定时日报仍可使用 bot 身份；严格发送规则仅应用于人工“提醒面试官”。

### 4.2 服务端权威数据查询

接口只信任 URL 中的面试记录 ID和当前用户身份，不再把前端传来的候选人字段作为事实来源。

查询链路：

1. 按 `interviews.id` 读取面试记录。
2. 优先使用 `interviews.resume_id` 关联 `resumes.id`。
3. 兼容历史数据：没有 `resume_id` 时，只在候选人姓名唯一匹配的情况下回退关联；存在重名时返回错误，禁止猜测。
4. 按面试官姓名从 `interviewer_mappings` 和 `users` 解析同一飞书应用下的 `open_id`。
5. 按 `resume.id` 从 `resume_files` 元数据和 `RESUMES_KV` 读取 PDF。

### 4.3 字段归一化

卡片字段及优先级：

| 展示字段 | 优先级 |
| --- | --- |
| 姓名 | `resumes.candidate_name` → `interviews.candidate_name` |
| 学历 | `parsed_data.highest_degree` → 归一化后的 `resumes.education` → `未识别` |
| 年龄 | `parsed_data.age` → 根据 `birthday` 计算 → `未识别` |
| 性别 | `parsed_data.gender` → `resumes.gender` → `未识别` |
| 岗位 | `resumes.mapped_position` → `resumes.position_applied` → `interviews.position_applied` |
| 面试时间 | `interviews.interview_time`，按北京时间格式化 |
| 城市 | `parsed_data.city` → `resume_screening_queue.city` → `recruitment_tasks.city` → 岗位地点 → `未识别` |

年龄计算基于报告/发送当天的北京时间，仅在生日字段可安全解析时计算。

### 4.4 AI 建议

人工点击提醒时不新增 AI 调用，优先复用已保存结果，避免发送等待和额外成本。

来源优先级：

1. `resumes.ai_evaluation`
2. `resumes.ai_review`
3. `resume_screening_queue.ai_analysis`
4. 固定文案“暂无 AI 建议，请结合简历原文评估”

展示内容压缩为三部分：

- 推荐结论/匹配概述。
- 1～2 个需要核实的风险点。
- 1～2 个建议追问方向。

卡片正文限制长度，超长内容在语义边界截断，禁止直接输出未解析的 JSON。

### 4.5 卡片结构

标题：`📅 面试提醒｜候选人姓名`

正文：

1. 两列或紧凑字段区展示七个基本字段。
2. 分隔线。
3. `🤖 AI 面试建议`。
4. 附件状态提示：`简历 PDF 将在下一条消息发送` 或 `简历附件暂不可用`。
5. 页脚：`操作者姓名 推荐｜AI 智能面试系统`。

### 4.6 PDF 发送顺序和部分失败

发送顺序：

1. 完成面试、简历、面试官和发送者校验。
2. 尝试读取并上传 PDF，提前获得 `file_key`。
3. 发送卡片。
4. 若有 `file_key`，发送 PDF 文件消息。
5. 记录发送结果和耗时，不记录 PDF、完整 AI 文本等敏感内容。

接口返回：

```json
{
  "ok": true,
  "card_sent": true,
  "file_sent": true,
  "sent_as": "当前用户姓名",
  "warning": null
}
```

部分成功时 `ok` 仍表示提醒卡片已经送达，同时 `file_sent=false` 且提供可展示的 `warning`。卡片失败时接口整体失败；文件消息不继续发送。

### 4.7 前端反馈

- 卡片和附件都成功：`已用你的飞书账号提醒面试官，并发送简历 PDF`。
- 卡片成功、附件失败：使用 warning 提示，不显示完全成功。
- 当前用户未授权：提示前往“个人设置 → 飞书授权”。
- 面试官未映射：提示前往“设置 → 面试官管理”。
- 请求期间禁用当前行按钮；允许用户之后主动再次提醒，不做永久去重。

## 5. 招聘日报设计

### 5.1 负责人和表格

负责人固定顺序：

1. 何雨菱
2. 杜雁玲
3. 魏秋柠

列定义：

| 列 | 统计口径 |
| --- | --- |
| 负责人 | 固定负责人姓名 |
| 开放岗位 | 生成时状态为 `open`/`published` 的岗位数 |
| 今日新增 | 报告日创建的简历数 |
| 待初筛 | 生成时仍处于待筛状态的简历数 |
| 今日通过 | 报告日完成筛选且最终为通过的简历数 |
| 今日淘汰 | 报告日完成筛选且最终为淘汰的简历数 |
| 今日面试 | `interview_time` 位于报告日的面试数 |
| Offer | `sent_at` 位于报告日的正式 Offer 数 |
| 入职 | `onboard_date` 等于报告日的入职数 |

所有日期边界按 `Asia/Shanghai` 计算，禁止使用 UTC 日界线直接统计。

负责人归属优先通过 `positions.responsible_person`，兼容 `position_mappings.responsible_person`。无法唯一映射的记录计入 `unassigned`，不猜测负责人。

### 5.2 快照与历史稳定性

生成日报时一次性计算：

- 三位负责人的所有列。
- 合计行。
- 未分配数量。
- 数据生成时间与统计日期。

结果保存到 `daily_reports.stats` JSON 快照；`candidate_details` 继续作为候选人明细快照。查看和发送历史日报均读取快照，不重新统计当前数据库。

同一日期允许人工重新生成一份新日报，但每份日报自己的快照保持不变。

### 5.3 AI 分析

AI 输入仅包含去标识化的三行统计、合计和未分配数量，不包含候选人姓名、联系方式或简历正文。

输出控制在 100～150 个中文字符，重点包括：

- 当日工作量或推进量最高的负责人。
- 最明显的流程堵点。
- 次日一条可执行建议。

AI 调用失败时使用确定性规则摘要，不阻断日报生成或发送。

### 5.4 手动和定时链路统一

提取共享函数：

- `buildDailyReportSnapshot(db, reportDate)`
- `generateDailyReportSummary(env, snapshot)`
- `buildDailyReportFeishuCard(report)`
- `sendDailyReport(...)`

以下入口复用它们：

- `POST /api/daily-reports/generate`
- `POST /api/daily-reports/:id/send`
- `POST /api/cron/daily-report`

定时日报先生成并保存快照，再发送同一份快照，避免“页面日报”和“飞书日报”数字不一致。

## 6. 飞书权限和限制

- 当前用户 OAuth 需要 `im:message` 与 `im:message.send_as_user`。
- 应用需要“获取与上传图片或文件资源”权限，并发布包含该权限的应用版本。
- PDF 使用飞书 IM 文件上传接口，文件不能为 0 字节且不得超过 30 MB。
- 面试官必须处于应用可用范围内，并能通过系统映射得到同一应用下的 `open_id`。
- 权限不足时接口返回可操作的错误，不静默切换发送者。

## 7. 安全与隐私

- 后端按面试 ID 和当前用户权限读取数据，不信任前端候选人字段。
- 日志只记录面试 ID、简历 ID、接收人映射结果、发送阶段、飞书错误码和耗时。
- 日志不记录 PDF 内容、原始简历文本、联系方式或完整 AI 分析。
- 日报 AI 输入不包含候选人个人信息。
- PDF 文件消息只发给配置的面试官，不发到默认招聘群作为失败兜底。

## 8. 测试与验收

### 8.1 Worker 单元测试

- 七个候选人字段的每一级回退。
- 出生年月转年龄及非法日期。
- AI 结果对象、字符串、非法 JSON和缺失情况。
- 严格发送不降级其他用户或 bot。
- PDF 上传成功、文件缺失、超过 30 MB、上传失败、文件消息失败。
- 重名且无 `resume_id` 时拒绝猜测。
- 三位负责人统计、未分配、北京时间边界、Offer 和入职口径。
- 历史日报发送读取快照而非实时数据库。
- AI 摘要失败时的规则兜底。

### 8.2 前端验证

- 面试提醒按钮 loading 和防重复点击。
- 完全成功、部分成功、需要重新授权、缺少面试官映射的提示。
- 招聘日报详情和飞书发送入口不回归。
- TypeScript 构建通过。

### 8.3 本地端到端验证

- 使用本地 D1 的一条完整简历和测试面试记录生成卡片 JSON。
- 使用模拟飞书 API 验证请求顺序：上传文件 → 发送卡片 → 发送文件。
- 使用 agent-browser 验证面试管理按钮和招聘日报页面。
- 未经明确生产部署确认，不调用生产发送接口做真实消息测试。

## 9. 发布策略

1. 独立分支完成实现与自动化测试。
2. 本地 D1 和模拟飞书接口验收。
3. 本地页面人工验收。
4. 检查飞书应用文件权限。
5. 合并前再次运行完整 Worker 测试和前端构建。
6. 只有在用户明确确认后，才推送 `main` 并触发生产部署。
