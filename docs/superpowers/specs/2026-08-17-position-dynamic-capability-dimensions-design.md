# 岗位动态能力维度评估适配设计

## 1. 背景

岗位管理允许为不同岗位配置不同数量和名称的能力维度，但当前简历 AI 评估链路仍将旧的 7 个维度作为全局固定协议。

例如，护士岗位配置了 4 个维度，AI 评估仍会补齐并保存“核心画像、企业背景、避坑雷区”等旧维度，导致提示词、结构化校验、加权判定和前端展示与岗位配置不一致。

## 2. 目标与非目标

### 目标

- AI 评估维度完全由当前岗位配置决定。
- 支持任意正整数数量的岗位维度，包括 3、4、5、6、7 项及以后更多维度。
- AI 提示词、结构化校验、补评分、服务端加权判定、数据库保存和前端展示使用同一份岗位维度配置。
- “关键词匹配”和“避坑雷区”只有在当前岗位配置时才启用对应门槛。
- 兼容未配置能力维度的历史岗位，避免旧岗位突然失效。

### 非目标

- 不改变现有岗位维度的编辑方式。
- 不自动改写历史简历已经保存的评估结果。
- 不删除旧的 7 维度数据；历史结果通过重新评估逐步更新。

## 3. 核心规则

### 3.1 岗位维度清单

每次评估先解析当前岗位的有效维度清单：

1. 优先读取 `capability_dimensions` 独立表中该岗位的非空配置。
2. 独立表没有有效配置时，读取 `positions.capability_dimensions`。
3. 两处都没有有效配置时，进入 legacy 兼容模式，使用旧的 7 项维度。

一旦岗位存在非空自定义配置，AI 只能使用这份配置，不能追加旧的默认维度，也不能因为数量不是 4 或 7 而回退到固定列表。

岗位维度配置应在进入评估链路时归一化为：

```ts
type PositionScreeningDimension = {
  name: string;
  description: string;
  weight: number | null;
  isGate: boolean;
};
```

其中 `isGate` 仅对 `关键词匹配` 和 `避坑雷区`生效。

### 3.2 AI 输出协议

动态协议必须追加到当前请求的最终评估上下文中，明确要求：

```text
本次岗位只评估以下 N 个维度：
1. 维度一
2. 维度二
...

必须且只能返回以上维度，不得返回其他岗位或系统默认维度。
```

全局系统提示词不得再写死“七个维度”。岗位专属动态协议优先级高于系统中的旧版固定维度描述。

### 3.3 结构化校验与补评分

所有结构化输出函数必须接收 `requiredDimensionNames` 参数：

- 自定义岗位：校验当前岗位的全部维度。
- legacy 岗位：校验旧 7 项维度。

主评估缺少维度时，只补当前岗位缺少的维度。

AI 返回额外维度时，服务端不将额外维度持久化；最终保存结果必须按岗位配置顺序过滤、去重。

### 3.4 门槛规则

- 当前岗位配置了 `关键词匹配`：检查关键词最低分。
- 当前岗位配置了 `避坑雷区`：检查避坑雷区最低分。
- 当前岗位未配置对应维度：该门槛不启用，不生成失败结果，也不展示该门槛。
- 多个已启用门槛必须全部通过。

### 3.5 加权规则

- 只有当前岗位的普通维度参与加权。
- `关键词匹配` 和 `避坑雷区`不参与普通加权分。
- 当前岗位配置了正权重时，按正权重计算。
- 当前岗位没有正权重时，对普通维度使用等权平均。
- 岗位没有任何普通维度时，岗位配置应在保存或评估前被拒绝；不能产生没有分母的加权结果。
- 加权分仍采用 0—5 分制，系统/岗位配置的最低分规则继续适用。

## 4. 组件与数据流

### 4.1 统一岗位评估配置解析器

新增或扩展共享解析函数，统一返回：

- 标准岗位名称
- 岗位职责和要求
- 个性化要求
- 动态能力维度数组
- 当前岗位初筛规则
- legacy 兼容标识

以下入口必须使用该解析结果，禁止各自重新拼接固定 7 项：

- D1 简历处理队列
- R2 简历处理队列
- 单份简历 AI 初筛
- 单份重新评估
- 批量重新评估
- `resume_screening` 队列记录评估
- 补充能力维度评分

### 4.2 评估流程

```text
简历/岗位输入
  ↓
解析岗位配置（任意 N 项维度）
  ↓
构建动态提示词
  ↓
AI 返回 JSON
  ↓
按当前岗位 N 项校验
  ↓
仅补当前岗位缺失项
  ↓
过滤额外维度并按配置排序
  ↓
执行当前岗位已启用门槛
  ↓
计算当前岗位普通维度加权分
  ↓
保存并展示 N 项结果
```

### 后端

- `worker/src/resume-processing/dimension-scores.ts`
  - 所有完整性校验、合并和缺失维度函数改为接收动态维度列表。
- `worker/src/resume-processing/structured-output.ts`
  - 修复提示词和结构化校验改为使用动态维度列表。
- `worker/src/resume-processing/weighted-screening.ts`
  - 普通维度、门槛维度和权重计算改为按岗位配置动态处理。
  - 全局提示词改为岗位无关，不再写死七项。
- `worker/src/resume-consumer.ts`
  - D1/R2 消费路径、补评分和最终校验全部传入当前岗位维度列表。
- `worker/src/index.ts`
  - 单份评估、重新评估、批量兼容路径和初筛队列路径统一使用动态配置。
- 共享岗位上下文解析逻辑
  - 同时返回格式化文本和结构化维度数组，避免重复解析或使用不一致来源。

### 前端

- `frontend/src/utils/resumeEvaluation.ts`
  - 继续按保存结果渲染实际维度数量。
  - 门槛标签只展示实际存在的门槛结果。
- 简历列表、简历详情、导出相关组件
  - 不再使用固定 7 项文案或固定数量判断。
- 系统设置和岗位维度配置文案
  - 将“五项能力加权”改为“岗位普通维度加权”。

## 6. 历史数据策略

代码上线后，历史 7 维度结果不会自动改变。对于护士等已经配置自定义维度的岗位，应使用批量重新评估重新生成结果。

重新评估后：

- 护士配置 4 项 → 保存并展示 4 项。
- 其他岗位配置 5 项 → 保存并展示 5 项。
- 其他岗位配置 6 项 → 保存并展示 6 项。
- 原有 7 项岗位 → 保持 7 项。
- 未配置维度的旧岗位 → 使用 legacy 7 项兼容模式。

## 7. 验收标准

- 4 项岗位不会出现第 5—7 项旧维度。
- 5 项、6 项以及任意其他数量的岗位均能完整评估。
- AI 返回额外旧维度时，数据库最终只保存当前岗位配置的维度。
- 当前岗位未配置“避坑雷区”时，不会因为该维度缺失而失败。
- 当前岗位配置门槛时，门槛仍能正确参与判定。
- 加权分只使用当前岗位普通维度，权重和等权兜底均正确。
- D1、R2、单份、批量、重新评估路径行为一致。
- 前端维度数量、总分上限、门槛标签与岗位配置一致。
- 旧 7 项岗位和未配置维度的历史岗位保持兼容。
- 前端和 Worker 测试全部通过，生产部署通过 GitHub Actions 完成。
