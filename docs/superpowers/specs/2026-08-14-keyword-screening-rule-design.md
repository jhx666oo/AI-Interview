# 简历 AI 初筛关键词规则优化设计

## 1. 背景

当前简历 AI 初筛将「关键词匹配」和「避坑雷区」都作为 5 分硬门槛。对于具备部分智能硬件、IoT、嵌入式产品经验，或具备知名企业相关经历的候选人，这个规则过于严格，导致候选人即使具备可用的相关背景，也可能因为关键词维度未达到 5 分而直接被淘汰。

本次调整只放宽「关键词匹配」规则，同时保留整体加权评分和「避坑雷区」的风险控制能力。

## 2. 目标与非目标

### 目标

1. 将「关键词匹配」明确拆成三个证据点，减少模型自由发挥造成的评分漂移。
2. 三个证据点中，命中任意一个完整证据点即可获得至少 2 分；关键词匹配达到 2 分或 3 分时，不再因该门槛直接淘汰。
3. 保留「避坑雷区」5 分硬门槛和原有五项能力加权评分规则。
4. 统一本地上传、邮件同步、飞书导入、队列消费和批量重评估等所有初筛入口的规则。
5. 将新规则同步到系统设置中的 `resume_screening` 和 `resume_screening_supplement` 提示词，并处理已经保存的旧提示词。

### 非目标

1. 不修改「企业背景」这个独立能力维度的普通评分逻辑。
2. 不修改五项能力维度的权重和加权分通过线（当前为 4 分）。
3. 不建立固定的知名企业白名单；企业是否知名由简历事实和模型综合判断，不能仅因公司名称本身通过。
4. 不因单独出现一个关键词就认定候选人满足 5 年相关经验。

## 3. 新的关键词匹配规则

「关键词匹配」继续输出 0–5 分整数，但必须基于以下三个证据点判断。每个证据点内部满足一个有效子条件即可算该证据点成立。

### 证据点一：相关经验

必须同时满足：

1. 有 5 年及以上智能硬件、IoT 或嵌入式相关产品经验；
2. 明确命中以下任一相关关键词或等价表述：
   - 嵌入式固件；
   - IoT 云平台；
   - MQTT 协议；
   - 设备端需求；
   - OTA 升级；
   - 软硬件联调。

仅出现关键词但无法证明 5 年以上相关经验，不算该证据点完整命中。

### 证据点二：外部开发协同

简历中必须有明确的 ODM、外包开发团队或外部研发团队对接经历，并且包含需求管控、需求拆解、进度/质量管理、验收或交付等明确职责描述。

仅写“负责供应商管理”“负责项目协同”等无法判断与外部开发及需求管控直接相关的泛化描述，不应直接认定为完整命中。

### 证据点三：知名企业相关经历

必须同时满足：

1. 曾在具有较强行业知名度的企业工作，例如京东、小米、海尔等同类企业；
2. 该段工作内容与智能硬件、IoT 或嵌入式产品直接相关。

知名企业背景本身不能替代智能硬件相关经历。

## 4. 评分口径

模型需要在「关键词匹配」的 `reason` 中分别说明三个证据点是否命中，并引用简历原文中的事实依据。推荐按以下口径输出分数：

| 分数 | 评分含义 | 初筛门槛 |
| --- | --- | --- |
| 0 | 没有相关证据 | 不通过关键词门槛 |
| 1 | 只有模糊、间接或无法核实的相关描述 | 不通过关键词门槛 |
| 2 | 三个证据点中至少完整命中一个 | 通过关键词门槛 |
| 3 | 至少完整命中两个证据点 | 通过关键词门槛 |
| 4 | 三个证据点均命中，但证据深度一般 | 通过关键词门槛 |
| 5 | 三个证据点均命中，且有明确、连续、可验证的成果或职责证据 | 通过关键词门槛 |

「关键词匹配」的服务端通过条件调整为 `score >= 2`。因此 2 分和 3 分不会再因关键词门槛被直接判定为不通过。

## 5. 整体初筛判定

服务端继续作为最终判定来源，不信任模型返回的 `match_score` 或 `recommendation` 字段：

1. 关键词匹配：`score >= 2`；
2. 避坑雷区：`score >= 5`；
3. 两个门槛都满足后，计算任职要求、企业背景、加分项、核心画像、核心职责五项能力的加权分；
4. 加权分仍按现有规则判断，当前加权分达到 4 分才最终通过。

因此，本次调整的含义是“关键词 2/3 分不再触发硬拒绝”，并不意味着关键词为 2 分时可以绕过整体能力加权分或避坑雷区判断。

建议将服务端常量拆分为两个清晰的阈值，例如：

```ts
const KEYWORD_MATCH_MIN_SCORE = 2;
const RED_FLAG_MIN_SCORE = 5;
```

失败原因同步改为“关键词匹配未达 2 分”，避免前端和日志继续显示旧的“未达 5 分”。

## 6. 提示词同步策略

### 6.1 统一提示词来源

继续使用 `WEIGHTED_SCREENING_PROMPT` 作为代码内的规则基准，并同步更新：

- `resume_screening` 的默认系统提示词；
- `resume_screening_supplement` 的默认系统提示词；
- 本地上传和 Resume Consumer Worker 使用的系统提示词；
- 飞书导入、批量重评估和其他调用 `getAIPrompt` 的初筛入口。

提示词必须明确：

- 只能输出七个既定能力维度；
- 每项为 0–5 整数，并提供中文事实依据；
- 关键词匹配按三个证据点评分；
- 关键词匹配 2 分或以上通过该门槛；
- 避坑雷区仍需 5 分；
- 最终是否通过由服务端计算。

### 6.2 已有系统设置提示词

只更新默认代码常量是不够的，因为生产数据库中的系统设置提示词优先级高于默认值。实施时增加一次可审计的提示词迁移：

1. 对 `system_configs.prompt_configs` 中的 `resume_screening` 和 `resume_screening_supplement` 进行版本化更新；
2. 如果提示词仍包含旧的“关键词匹配与避坑雷区均为 5 分硬门槛”内置文本，则只替换该旧规则段，保留用户额外添加的其他内容；
3. 如果无法识别旧规则段，则保留用户自定义正文，并追加带版本标识的新规则段，避免运行时继续使用旧门槛；
4. 默认种子接口同步使用新版本，避免后续重新初始化时恢复旧规则；
5. 迁移过程记录更新时间和规则版本，不记录简历内容或敏感信息。

这样既能让系统设置页面看到新规则，又不会无条件覆盖用户自定义提示词。

## 7. 前端展示调整

1. 将关键词门槛失败文案从“关键词匹配未达 5 分”改为“关键词匹配未达 2 分”。
2. 继续展示关键词匹配实际分数和依据，避免用户误以为 2 分代表完全匹配。
3. 避坑雷区仍显示原有风险门槛说明。
4. 更新前端工具函数和单元测试中的旧文案断言。

## 8. 测试设计

### 服务端单元测试

覆盖以下场景：

1. 关键词 0 分：关键词门槛失败；
2. 关键词 1 分：关键词门槛失败；
3. 关键词 2 分、避坑雷区 5 分：通过关键词门槛，并进入加权分计算；
4. 关键词 3 分、避坑雷区 5 分：通过关键词门槛，并进入加权分计算；
5. 关键词 5 分、避坑雷区 4 分：仍因避坑雷区失败；
6. 两个门槛满足但加权分不足 4 分：最终仍不通过；
7. 两个门槛满足且加权分达到 4 分：最终通过；
8. 失败原因不再出现旧的“关键词匹配未达 5 分”。

### 提示词与配置测试

1. 断言代码内统一提示词包含三个证据点和新阈值；
2. 断言默认提示词不再声明关键词必须 5 分；
3. 覆盖旧系统设置提示词的安全替换或追加逻辑；
4. 验证所有初筛入口继续使用同一规则常量。

## 9. 验收标准

1. 一份关键词匹配 2 分、避坑雷区 5 分且加权分达标的简历可以通过初筛。
2. 一份关键词匹配 3 分、避坑雷区 5 分且加权分达标的简历可以通过初筛。
3. 关键词匹配 0–1 分的简历仍会被关键词门槛拦截。
4. 避坑雷区低于 5 分的简历仍会被拦截。
5. 系统设置页面显示的新提示词与实际评估规则一致。
6. 本地上传、邮件、飞书和批量重评估不出现规则分叉。
7. 前端、服务端测试和类型检查通过。

## 10. 回滚方案

如果上线后通过率明显异常，可回滚以下内容：

1. 将 `KEYWORD_MATCH_MIN_SCORE` 恢复为 5；
2. 回滚提示词规则版本；
3. 保留本次新增的测试，以便明确验证旧规则恢复情况。

本次设计不涉及生产数据删除，也不改变简历原文、历史评估结果或岗位配置数据。
