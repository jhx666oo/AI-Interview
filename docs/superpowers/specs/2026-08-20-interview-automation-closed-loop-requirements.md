### 2.2 当前缺口与风险

| 编号 | 现状 | 影响 | 本期要求 |
|---|---|---|---|
| G-01 | 业务筛选通过后不会自动创建下一步 | 仍需 HR 手工交接 | 幂等创建“待安排面试”记录 |
| G-02 | 飞书日程绑定在“开始面试”按钮 | 创建时机太晚，候选人不能提前收到安排 | 改为“确认时间后安排”，开始面试只改状态 |
| G-03 | 无有效面试时间时会回退到当前时间，且可自动改写原面试时间 | 可产生意外日程 | 时间缺失时只进入 `awaiting_schedule`，不建日程 |
| G-04 | 候选人邮件和面试官提醒使用 `waitUntil` | 实例终止时可丢任务，无统一重试 | 改为 D1 作业表 + Cloudflare Queue |
| G-05 | 只记录邮件最后发送时间，飞书通知缺少独立投递记录 | 无法精准重发、查询部分成功 | 新增通知日志与去重键 |
| G-06 | 一面/二面既有 `round`，又有 `evaluation2/result2/status2` | 数据口径不一致 | 新链路统一为每候选人每轮一条 `interviews` 记录 |
| G-07 | 公开面试卡片 token 可提交评价，候选人邀请 token 可改期 | 链接转发后可越权改写 | 一期公开链接只读；评价和改期走登录态 |
| G-08 | 取消面试接口会删除人才库记录 | 取消一场面试可导致候选人档案丢失 | 立即解耦：取消只更新面试/日程/通知 |
| G-09 | 缺少下一轮关联、调度状态、失败原因和版本号 | 难以正确恢复中断流程 | 扩展数据模型并提供人工重试 |
| G-10 | 本地 `main` 落后 GitHub 最新代码 | 直接实施会重复或覆盖新功能 | 实施前必须从 `origin/main@eb99be4` 新建隔离工作区 |

### 2.3 现状结论

当前系统已经具备面试闭环所需的大部分“单点能力”，一期重点不是继续增加孤立按钮，而是用统一状态、幂等作业和审计事件把它们连起来。

## 3. 业务背景与目标

### 3.1 当前问题

候选人在 AI 初筛、HR 入库、业务筛选、面试安排、面试评价之间，仍需多次人工复制信息、重复点击通知、记忆下一轮。系统能“做某件事”，但不能可靠地“把整件事做完”。

### 3.2 一期目标

建立以 D1 为业务状态真相源的面试自动化闭环：

1. AI 初筛结束后，系统可按配置自动生成业务筛选待办。
2. 业务筛选通过后，系统幂等创建下一轮“待安排面试”。
3. HR 确认时间后，系统异步建立飞书日程/会议，通知面试官，并给候选人发邮件。
4. 面试官在授权页面查看简历、AI、HR、业务筛选和前序评价，提交当前轮结果。
5. 当前轮通过后，系统自动创建下一轮待安排记录；末轮通过则进入待 HR 确认的后续阶段。
6. 任何自动动作都可查询、可重试、可人工接管，且不因外部通知失败丢失业务数据。

### 3.3 可量化目标

| 指标 | MVP 目标 | 生产收口目标 |
|---|---:|---:|
| 业务通过→下一轮记录创建 | 95% 在 60 秒内 | 99.5% 在 60 秒内 |
| 有完整调度数据的日程创建 | 95% 在 2 分钟内 | 99% 在 2 分钟内 |
| 重复点击导致的重复面试/日程 | 0 | 0 |
| 通知失败导致的面试记录丢失 | 0 | 0 |
| 自动作业可追踪率 | 100% | 100% |
| 关键动作审计覆盖率 | 100% | 100% |

## 4. 范围与边界

### 4.1 MVP 必须包含

1. 全局主开关与岗位级开关控制的 AI 初筛后自动业务筛选。
2. 业务筛选通过后自动创建待安排的一面记录。
3. 一面通过后自动创建待安排的二面记录。
4. 安排、改期、取消面试的 D1 状态、飞书日程同步和邮件/飞书通知。
5. 通知失败独立重发，不回滚面试记录。
6. 统一面试上下文：简历原件、OCR/字段、AI 初筛、HR 备注、业务评价、历史面试评价和时间线。
7. 公开 token 页面只读；提交评价、改期、取消必须登录并经权限校验。
8. 全链路幂等、重试、人工接管、操作日志和运行指标。

### 4.2 MVP 不包含

1. 自动决定是否录用、自动发 Offer、自动签约或自动入职。
2. 飞书会议室、物理会议室的资源抢占。
3. 候选人短信、微信或外部招聘网站消息。
4. 自动录音、实时转写和面试视频归档。
5. AI 初筛维度、权重和提示词的重新设计。
6. 三轮以上的可视化流程设计器。数据模型保留扩展能力，MVP 界面只支持一面和二面。

### 4.3 7 天 MVP 与生产收口的切线

7 个工作日的目标是完成一个岗位、一组面试官、一面→二面的可验收闭环，并完成主要异常的人工重试。要达到几十人使用、每日数百至数千份简历的生产可靠性，预留 3–8 个工作日进行压测、灰度和运行调优。

## 5. 产品原则

### 5.1 D1 是业务状态真相源

- 面试记录、调度状态、业务结果、面试结果、通知状态和自动作业都先落 D1。
- 飞书日程、飞书消息和邮件是外部副作用，失败不得删除或回滚业务主记录。
- 列表、仪表盘、日报和时间线统一读 D1，不以飞书是否发送成功判断业务进度。

### 5.2 AI 提供建议，人做关键决策

- AI 可以触发自动推送，但业务筛选、面试通过/淘汰必须由授权用户确认。
- AI 不得因性别、年龄等敏感信息自动做录用或淘汰决策。
- 字段缺失、配置不完整或规则冲突时，进入人工处理，不自动拒绝候选人。

### 5.3 重要动作必须幂等、可追踪、可恢复

- 同一候选人同一轮只允许一条有效面试。
- 同一面试同一动作只允许一个活动作业。
- 同一接收人、同一渠道、同一模板、同一业务版本只发送一次。
- 重试只重试失败步骤，不重复已成功的日程或通知。

### 5.4 公开链接最小权限

- 面试卡片链接：仅向授权业务协作对象分享受限读取信息，MVP 不提供写操作。
- 候选人邀请链接：只展示候选人自己的安排，不展示 AI、HR、业务和面试评价。
- 改期、取消、提交评价必须经过登录、角色和面试归属校验。

## 7. 统一业务流程

### 7.1 主流程

```text
简历入库
  → OCR / 字段提取
  → AI 初筛
      ├─ 不通过：HR 人工复核或结束
      └─ 通过：根据开关自动生成/追加业务筛选待办
          → 业务负责人通过/淘汰
              ├─ 淘汰：结束当前候选流程
              └─ 通过：创建一面记录（awaiting_schedule）
                  → HR 确认面试时间/形式/地点
                  → 异步创建飞书日程和会议链接
                  → 异步通知面试官 + 候选人
                  → 面试官登录后提交一面评价
                      ├─ 不通过：结束面试流程
                      └─ 通过：创建二面记录（awaiting_schedule）
                          → 重复安排/通知/评价
                              ├─ 不通过：结束面试流程
                              └─ 通过：进入 pending_offer_review，等待 HR 处理
```

### 7.2 关键纠正：业务通过不等于立即建日程

业务通过时通常还没有面试日期和开始时间。因此：

- 如果时间、面试官和方式不完整，系统只创建 `awaiting_schedule` 面试记录。
- 如果必填调度字段已完整，可自动进入 `schedule_queued`。
- 系统不得用“当前时间”填充缺失时间，不得未经确认自动改写已录入时间。

### 7.3 一人多轮的数据口径

- 每一轮面试独立一条 `interviews` 记录，通过 `resume_id + round` 定位。
- `previous_interview_id` 和 `next_interview_id` 串联轮次。
- 新链路只写当前记录的 `evaluation/result/status`。
- 现有 `evaluation2/result2/status2` 仅作历史数据兼容展示，不再作为新二面的真相源。

## 8. 状态模型

### 8.1 候选人业务阶段

| 阶段 | 含义 | 触发条件 | 允许下一步 |
|---|---|---|---|
| `ai_pending` | AI 尚未完成 | 简历刚入库 | 重试、人工复核 |
| `ai_passed` | AI 建议通过 | AI 任务成功 | 业务筛选或 HR 处理 |
| `ai_rejected` | AI 建议不通过 | AI 任务成功 | HR 覆盖或结束 |
| `business_pending` | 等待业务筛选 | 生成业务待办 | 业务通过/淘汰 |
| `business_passed` | 业务通过 | 业务决策 | 创建待安排面试 |
| `business_rejected` | 业务淘汰 | 业务决策 | HR 覆盖或结束 |
| `interviewing` | 存在未结束面试 | 一面/二面创建 | 安排、评价、下一轮 |
| `pending_offer_review` | 末轮通过 | 二面通过 | HR 确认后续 |
| `rejected` | 流程结束 | HR/业务/面试不通过 | 管理员/HR 审计覆盖 |
| `manual_review` | 缺配置或自动处理失败 | 业务规则触发 | HR 补齐、重试、取消 |

### 8.2 单轮面试状态

| `interviews.status` | 含义 |
|---|---|
| `awaiting_schedule` | 已创建轮次，待 HR 填写/确认时间 |
| `schedule_queued` | 调度作业已入队 |
| `scheduled` | D1 已确认时间，飞书日程已创建 |
| `notification_partial` | 日程成功，部分通知失败 |
| `in_progress` | 面试已开始 |
| `awaiting_evaluation` | 面试已结束，待提交评价 |
| `completed` | 本轮评价已提交 |
| `cancelled` | 本轮面试已取消 |
| `manual_review` | 调度或推进需人工处理 |

### 8.3 调度状态

| `schedule_status` | 含义 |
|---|---|
| `not_ready` | 时间或面试官不完整 |
| `queued` | 创建/更新/取消作业已入队 |
| `scheduled` | 外部日程同步成功 |
| `reschedule_pending` | 改期等待外部同步 |
| `cancel_pending` | 取消等待外部同步 |
| `cancelled` | 外部日程已取消或本来不存在 |
| `failed` | 达到自动重试上限，待人工处理 |

### 8.4 通知状态

| 状态 | 含义 |
|---|---|
| `queued` | 已写通知记录并入队 |
| `sent` | 外部服务确认发送成功 |
| `failed` | 本次失败，仍可重试 |
| `skipped` | 受配置、缺联系方式或去重规则影响而跳过 |
| `cancelled` | 业务动作已取消，不再发送 |

## 9. 详细功能需求

### FR-01 AI 初筛后自动生成业务筛选待办

1. 新增全局开关 `INTERVIEW_AUTOMATION_ENABLED`，默认 `false`。
2. 新增岗位级开关 `auto_business_screening_enabled`，默认 `0`。
3. 仅当两个开关均开启、AI 任务完成、HR 状态允许且岗位能唯一确定业务负责人时，才自动推送。
4. 同一简历同一 AI 结果版本只能生成一次业务待办。
5. 无岗位、无面试官、同名岗位映射不唯一时，记录 `manual_review`，不使用姓名模糊推送。
6. 关闭开关后，现有 HR 手动推送功能完全保留。

### FR-02 业务筛选决策与面试创建

1. 业务通过时必须在同一 D1 事务边界内完成决策落库、时间线事件和推进作业创建。
2. 推进作业消费时，以 `resume_id + round=1` 幂等创建一面记录。
3. 岗位的一面面试官缺失或无法唯一解析时，面试记录仍保留，状态为 `manual_review`。
4. 业务淘汰时不创建面试，并记录业务评价、决策人、决策时间和批次。
5. 对已终结的业务决策重复提交相同结果返回幂等成功；提交相反结果返回 409，需 HR/管理员走审计覆盖。

### FR-03 安排面试

1. 入口：面试管理“安排面试”、候选人详情、业务通过后待办、失败重试。
2. 必填：候选人、岗位、轮次、主面试官、开始时间、时长、时区、面试方式。
3. 默认：时长 60 分钟，时区 `Asia/Shanghai`，线上面试创建飞书视频会议。
4. 可选：副面试官、线下地点、候选人说明、内部备注。
5. 提交后 API 立即返回 `202 Accepted + job_id`，不同步等待飞书或 SMTP。
6. 仅当 D1 写入成功且作业已入队时才向用户显示“已提交安排”。

### FR-04 飞书日程和会议

1. 自动作业统一使用系统配置的招聘日历 `FEISHU_RECRUITMENT_CALENDAR_ID`，不依赖触发者浏览器中的个人 OAuth token。
2. 未配置招聘日历时，调度作业进入 `failed/manual_review`，不默认创建到任意人的 `primary` 日历。
3. 日程包含：候选人、岗位、轮次、面试时间、方式、内部候选人详情链接。
4. 线上面试使用飞书原生视频会议；线下面试保留填写地点，不强制创建视频会议。
5. 主/副面试官仅在 `open_id` 唯一解析成功后加入参与人。无法解析的参与人不得使用同名首条替代。
6. 保存 `calendar_id`、`calendar_event_id`、`meeting_url`、外部返回摘要和错误代码。

### FR-05 面试官飞书提醒

飞书卡片至少展示：

- 候选人姓名、学历、年龄或出生年月、性别、应聘岗位、城市。
- 当前轮次、面试时间、时长、地点/会议链接。
- AI 初筛总结、优势、风险点、建议追问。
- HR 备注、业务筛选评价、前序面试摘要。
- 受限面试卡片链接按钮、简历 PDF 附件。

创建成功后提醒一次，面试前 30 分钟按幂等键再提醒一次。单个参与人发送失败不影响其他人。

### FR-06 候选人邮件

1. 发件配置使用系统“邮件设置”中已启用的 SMTP 配置，不硬编码发件人和密码。
2. 邮件包含：候选人姓名、岗位、面试轮次、时间、时长、方式、地点/会议链接、联系方式和注意事项。
3. 邮件不包含 AI 评分、HR 备注、业务评价或面试官内部评语。
4. 无候选人邮箱时，日程和面试官提醒继续，邮件记录为 `skipped`，并在面试管理显示原因。
5. 改期发送“面试时间更新”模板，取消发送“面试取消”模板，两者不与初次邀请共用去重键。

### FR-07 改期、取消和重发

1. 改期需要登录，修改 D1 时间和 `version`，然后创建 `reschedule` 作业。
2. 改期成功后更新日程，并给面试官和候选人发更新通知。
3. 取消只取消当前轮面试、外部日程和未发通知，不删除简历或人才库档案。
4. 取消原因、操作人和时间必须记录到时间线和操作日志。
5. 重发按渠道执行：可单独重发面试官卡片、PDF 或候选人邮件。
6. 如果当前面试 `version` 已变更，旧作业标记 `cancelled`，不再发送过期内容。

### FR-08 面试评价和自动推进

1. 评价字段：综合结论、能力/专业评分、优势、风险、关键问答、结果、提交人、提交时间。
2. 当轮面试官只能提交自己被分配的当轮评价。
3. 普通提交后评价不可直接覆盖；HR/管理员覆盖需填原因并生成审计事件。
4. 一面通过：幂等创建 `round=2` 面试记录，从岗位取二面面试官，状态为 `awaiting_schedule`。
5. 二面通过：候选人进入 `pending_offer_review`，不自动发 Offer。
6. 任一轮不通过：当前面试记录完成，候选人阶段进入 `rejected`，已创建的后续待安排面试需标记取消。
7. 下一轮面试官缺失、不唯一或无法匹配 `open_id` 时，创建记录但标记 `manual_review`，不发送通知。

### FR-09 统一面试上下文

内部授权页 `/interviews/:id/score` 必须展示：

1. 候选人概览：姓名、岗位、城市、学历、联系方式、当前阶段。
2. 简历：PDF 预览/下载、OCR 原文、结构化字段。
3. AI：总分、维度分、硬条件、优势、风险点、建议追问、模型和分析时间。
4. 人工处理：HR 备注、业务筛选结果/评价/操作人/时间。
5. 面试历史：每轮面试的安排、面试官、评分、评语和结果。
6. 时间线：简历入库、AI、HR、业务、日程、通知、评价、改期、取消和手动重试。
7. 操作：安排、开始、提交评价、通过、淘汰、创建下一轮、改期、取消、重发和下载简历。

公开面试卡片 `/interview-card/:token` 只展示其中的受限读取内容，联系方式脱敏，不显示系统操作按钮。

### FR-10 时间线、日志与运行面板

1. 每个候选人关键阶段变化写入 `candidate_stage_events`，使用唯一 `dedupe_key`。
2. 每个用户写操作写入 `operation_logs`，包含操作前后状态、对象、操作人和原因。
3. 每个自动动作写入 `interview_automation_jobs`，可查看当前步骤、尝试次数、下次重试时间和最后错误。
4. 每个外部通知写入 `interview_notifications`，保留渠道、收件人、模板、外部消息 ID 和投递结果。
5. HR/管理员可在面试详情查看失败步骤，对单个步骤执行重试。

### FR-11 仪表盘和招聘日报

1. 创建待安排面试后，候选人计入“待安排面试”，不计入“已安排”。
2. 只有日程创建成功后才计入“已安排面试”。
3. 面试评价提交后写入面试通过/不通过事件，仪表盘和日报从该事件口径汇总。
4. 已取消面试不计入已安排数，但在取消数和时间线中保留。

## 12. 可靠异步编排

### 12.1 基本架构

```text
用户/业务决策
  → API Worker 在 D1 写业务记录 + automation job
  → INTERVIEW_AUTOMATION_QUEUE
  → interview-automation-consumer
      ├─ 创建/更新/取消飞书日程
      ├─ 发送面试官卡片/PDF
      ├─ 发送候选人邮件
      ├─ 创建下一轮
      └─ 写回 D1 作业/通知/时间线/日志
```

### 12.2 重试策略

- 网络错误、429 和飞书/SMTP 5xx：指数退避，延迟为 1、5、15、60、240 分钟，最多 5 次。
- 缺配置、缺邮箱、缺 `open_id`、权限不足：不自动重试，直接进入人工处理。
- 已存在同一 `calendar_event_id`、同一通知 `dedupe_key`或同一下一轮记录：幂等成功，不再发送。
- 作业执行前重新加载面试 `version`。版本过期的作业标记 `cancelled`。

## 13. 异常处理

| 场景 | 系统处理 | 用户可见结果 |
|---|---|---|
| 候选人无邮箱 | 日程和面试官提醒继续，邮件 `skipped` | “未发送：候选人无邮箱” |
| 面试官无唯一 `open_id` | 不发卡片，面试进入人工处理 | 显示缺失的面试官姓名 |
| 缺面试时间 | 只创建 `awaiting_schedule` | 显示“待安排” |
| 缺招聘日历配置 | 日程作业失败，不发过期通知 | 管理员看到配置入口 |
| 日程创建成功但无会议链接 | 短延迟重读日程；仍无则标记部分成功 | 显示“日程已建，会议链接待同步” |
| 邮件失败 | 不回滚日程，单独重试邮件 | 显示邮件失败原因和重发按钮 |
| 飞书卡片成功、PDF 失败 | 卡片 `sent`，PDF `failed` | 可单独重发 PDF |
| 重复点击通过/安排 | 命中幂等键，返回原结果 | 不新建面试/日程 |
| 下一轮无面试官 | 创建下一轮记录并标记 `manual_review` | HR 可补充后安排 |
| 改期时旧通知仍在队列 | 旧版本作业取消 | 只收到新时间通知 |
| 取消飞书日程失败 | D1 仍保持已取消，日程作业可重试 | 显示“系统已取消，飞书待同步” |
| 公开链接过期/撤销 | 返回 410，不泄露候选人是否存在 | 统一提示联系 HR |

## 14. 非功能需求

### 14.1 性能与容量

- 面试列表、候选人上下文 API：P95 < 1.5 秒（不包含 PDF 文件传输）。
- 公开面试卡片 API：P95 < 2 秒，响应必须包含 `Cache-Control: no-store`。
- 单次批量业务通过 100 人时，API 在 2 秒内返回，后续面试创建由队列削峰。
- 消费者并发从 3 开始，根据飞书/SMTP 429 和 D1 写入延迟调整，不在首版盲目提高。

### 14.2 安全

- token 只存 SHA-256 哈希，不在 D1 存明文。
- 公开 API 使用统一过期/撤销语义，禁止返回用户、邮件密码、飞书 token、内部 ID 映射。
- 候选人邮箱、手机在面试官公开页面中脱敏，仅 HR/管理员登录态可看完整值。
- 操作日志不记录 SMTP 密码、OAuth token、完整简历原文或邮件正文。
- 对公开链接 API 增加 IP + token 维度限流和访问日志。

### 14.3 可观测性

必须可查询以下指标：

- 按 action 的作业数、成功率、部分成功率、失败率、重试次数和处理耗时。
- 飞书卡片、PDF、邮件按渠道和模板的投递成功率。
- `manual_review` 积压数、平均处理时长和主要错误代码。
- 业务通过→一面创建、一面通过→二面创建的耗时。

## 15. 前端交互需求

### 15.1 面试列表

- 增加“待安排”、“安排中”、“通知部分失败”、“需人工处理”筛选。
- 卡片/表格同时显示轮次、调度状态、飞书卡片状态、PDF 状态和候选人邮件状态。

- 提交后显示作业进度，日程成功后再显示会议链接。

### 15.3 评价页

- 前序评价默认折叠，当轮面试官可展开查看。
- 提交结果前二次确认，明确告知“通过将创建下一轮待安排面试”。

## 16. 验收标准

### 16.1 主流程

- [ ] 开启全局和岗位开关后，AI 通过的候选人只生成一份业务筛选待办。
- [ ] 业务通过后 60 秒内可在面试管理看到一面 `awaiting_schedule`。
- [ ] 未填时间时不创建飞书日程，不使用当前时间代替。
- [ ] HR 确认时间后只创建一个飞书日程，并保存日程 ID 和会议链接。
- [ ] 一面通过后只创建一条二面记录，并带出二面面试官。
- [ ] 二面通过后进入 `pending_offer_review`，不自动发 Offer。

### 16.2 通知与失败恢复

- [ ] 面试官收到卡片、简历 PDF 和受限面试卡片链接。
- [ ] 候选人收到不含内部评价的面试邮件。
- [ ] 卡片成功但 PDF 失败时，页面显示部分成功，可单独重发 PDF。
- [ ] 邮件失败不回滚面试和日程，可单独重发邮件。
- [ ] 连续重复点击安排、通过或重发，不产生重复日程、面试或消息。
- [ ] 作业达到重试上限后显示人工处理，可看到可理解的错误原因。

### 16.3 安全与数据保护

- [ ] 未登录用户不能通过面试卡片 token 提交评价。
- [ ] 未登录用户不能通过候选人邀请 token 改期。
- [ ] 过期或撤销链接返回 410，不泄露候选人是否存在。
- [ ] 取消面试不删除简历、人才库档案或历史评价。
- [ ] 非当轮面试官不能提交该轮评价。
- [ ] 所有 HR/管理员覆盖操作有原因和审计记录。

### 16.4 回归保护

- [ ] 现有简历上传、AI 初筛、手动入库/不入库可用。
- [ ] 现有手动业务筛选推送、公开页单人/批量决策可用。
- [ ] 现有面试列表、简历 PDF、面试官提醒、日报和仪表盘可用。
- [ ] 全局自动化开关关闭后，系统行为与改造前一致，除了取消面试不再删除人才档案这一安全修复。

## 17. 发布与灰度要求

1. 实施分支必须从最新 `origin/main` 创建，不从当前落后的本地 `main` 直接开发。
2. 所有 D1 migration 必须是只增不删，先部署 schema，再部署兼容代码。
3. 功能开关初始为 `false`，上线后先对 1 个内部测试岗位开启。
4. 灰度期至少完成 10 名候选人、一面→二面的完整流转，且 24 小时内无重复日程和越权写入。
5. 开启范围按“岗位”扩大，不一次性对全公司开启。
6. 回滚只关闭开关和回滚应用代码，不回滚已执行的 D1 migration，不删除已创建作业和通知记录。

## 18. 产品验收用例

### 用例 A：正常一面→二面

1. AI 初筛通过，系统自动将候选人放入业务待办。
2. 业务负责人提交通过和评语。
3. 面试管理出现一面待安排记录，不产生飞书日程。
4. HR 选择空闲时段并提交，页面先显示安排中，随后显示已安排。
5. 面试官收到飞书卡片和 PDF，候选人收到邮件。
6. 面试官登录系统提交一面通过。
7. 系统只创建一条二面待安排记录，并带出二面面试官。

### 用例 B：邮件失败但日程成功

1. HR 安排面试，飞书日程创建成功。
2. SMTP 返回失败，面试状态不回滚。
3. 页面显示“已安排，候选人邮件失败”。
4. HR 点击重发邮件，不再创建新日程，不重发已成功飞书卡片。

### 用例 C：缺少二面面试官

1. 一面评价通过。
2. 系统创建二面记录，但状态为 `manual_review`。
3. 系统不建日程、不发邮件、不将一面面试官默认当作二面面试官。
4. HR 补充二面面试官后，才可安排时间。

### 用例 D：取消面试

1. HR 填写取消原因并确认。
2. D1 面试记录立即标记取消，作业异步取消飞书日程并通知双方。
3. 候选人简历、人才库档案、AI 结果、业务评价和历史面试评价仍然存在。
