# 招聘运营仪表盘重构与快照设计

## 目标

将现有仅含 KPI 与事业部岗位表的仪表盘，升级为一张可纵向滚动的招聘运营看板。它应提供实时经营视图、不可变历史快照、可按事业部展开的岗位明细，以及安全的实时/固定快照分享链接。

本设计借鉴“五大事业部招聘看板”的信息层级，不复刻其红色主题；页面必须沿用现有系统的蓝紫色主色、浅色背景、白色 Ant Design 卡片、圆角与状态 Tag。

## 已确认的范围

### 单页信息结构

页面从上至下固定为：

1. 页头：看板标题、数据截止说明、数据版本选择器、分享与刷新操作。
2. 总体概览：在招岗位、在招人数、已入库简历、安排面试、面试通过率、发放 Offer、已入职、本周需求完成，共七张 KPI 卡片。
3. AI 智能总结：由确定性聚合指标生成“当前概况、漏斗短板、建议”的诊断区，不在页面加载时调用大模型。
4. 招聘漏斗：已入库简历、AI 初筛完成、安排面试、一面通过、二面通过、三面通过、Offer、入职的全局横向漏斗。
5. 事业部分部看板：每个事业部一张卡，显示 HRBP、岗位/人数/P0、关键漏斗指标与小型漏斗。
6. 招聘效能（按 HRBP）：每位 HRBP 一张卡，显示负责岗位、在招人数、平均招聘周期、P0 指标和个人漏斗。
7. 全量岗位明细汇总：按事业部聚合的一张宽表，含事业部、HRBP、在招职位、优先级、在招人数、简历、一面、一面通过、二面通过、三面通过、通过率、Offer、入职、备注、状态。

### 明细表交互

- 事业部汇总行是同一张表中的可折叠行，左侧使用 `▶` / `▼` 表示状态；不得渲染嵌套子表。
- 默认只展开排序后的第一个事业部；其余事业部收起。
- 筛选结果变化后，保留仍存在事业部的展开状态；新出现的首个事业部可展开。
- 表底始终显示“合计”行，合计基于当前数据版本和当前筛选范围。
- P0/P1/P2 与流程状态沿用现有 Tag 颜色；无数据以 `0` 或 `—` 明确表示。

### 数据版本与快照

- 选择器首项固定为“最新实时数据”，实时从当前 D1 数据聚合，不写入任何快照。
- 新表 `dashboard_snapshots` 按北京时间自然日保存日结的完整、脱敏聚合 DTO。字段为：`id`、`snapshot_date`（唯一）、`payload_json`、`generated_at`、`generated_by`（`cron` 或用户邮箱）、`created_at`。
- Cloudflare Worker 每天北京时间 23:55 自动生成日结快照。已有同日记录时跳过，快照永远不可覆盖。
- 管理员可手动补存缺失日期；若该日期已有快照，接口返回冲突，不能重写历史。
- 历史日期只读取 `payload_json`，因此岗位/简历/面试的后续补录、删除或修正不会改变历史看板。
- 现有 Cron 继续处理提醒；新增快照 Cron。时区转换使用 UTC 触发时间，快照日期统一以 `Asia/Shanghai` 计算。

### 分享

- 现有 `dashboard_share_links` 增加数据模式：`data_mode` 为 `live` 或 `snapshot`，固定快照时保存 `snapshot_id`。
- 创建分享链接时，管理员/HR 可选“最新实时数据”或某个已存在的快照。未选择快照即为实时分享。
- 实时分享每次读取实时聚合；快照分享只读取该快照 JSON，永久不漂移。
- 现有 token 哈希、过期、撤销、角色权限和匿名访问行为保持不变。
- 内部页与分享页复用同一看板显示组件；匿名分享页不出现侧边栏、筛选、刷新、快照补存、分享管理、候选人信息或 AI 原始评价。

## 数据口径

所有实时统计通过岗位 ID 关联，事业部和 HRBP 汇总均由岗位明细求和，不维护第二份汇总数据。

| 指标 | 口径 |
| --- | --- |
| 在招岗位 | `positions.status IN ('open','published')` 的岗位数 |
| 在招人数 | 在招岗位 `headcount` 之和 |
| 已入库简历 | 关联岗位的 `resumes` 总数 |
| AI 初筛完成 | `resumes.parse_status='ai_screened'` 的数量 |
| 安排面试 | 现有一面统计口径：有一面安排或一面通过记录的数量 |
| 1/2/3 面通过 | 对应轮次的通过面试记录数 |
| 面试通过率 | `三面通过 ÷ 安排面试`；无三面流程或分母为 0 时为 `null`，前端显示 `—` |
| Offer | 排除 `draft`、`cancelled` 的 Offer 数 |
| 入职 | `onboarding_records.status='onboarded'` 的数量 |
| 平均招聘周期 | 有效配对的 `resume.created_at` 到入职日期/入职记录创建时间的天数均值；无有效样本显示 `—` |
| 本周需求完成 | 第一版保留卡片但显示“暂未采集”，不使用入职数伪造需求完成数；后续引入需求完成事件后再填充 |

岗位若没有 `position_id` 关联的历史数据，沿用现有岗位名回退逻辑并标记 `unmatched`；看板仍展示，但不得将该类记录悄然归入错误岗位。

## API 与 DTO

### 统一看板 DTO

实时与快照均返回同一版本化 DTO，至少包括：

- `version`、`data_mode`（`live` / `snapshot`）、`snapshot_date`、`updated_at`；
- `kpis` 与其可用性说明；
- `funnel`（阶段数组及转化率）；
- `insights`（确定性摘要、短板、建议）；
- `divisions`（事业部卡片数据与岗位列表）；
- `hrbps`（负责人效能卡数据）；
- `totals`（明细表合计）。

建议接口：

- `GET /api/dashboard/recruiting-board?mode=live`：实时 DTO。
- `GET /api/dashboard/recruiting-board?mode=snapshot&date=YYYY-MM-DD`：历史 DTO。
- `GET /api/dashboard/snapshots`：可选快照日期列表。
- `POST /api/dashboard/snapshots`：管理员补存某个尚不存在的日期；默认当天。
- 现有分享创建接口接收 `data_mode` 和可选 `snapshot_id`；匿名分享接口按链接模式返回对应 DTO。

## 前端组件边界

- `Dashboard`：权限内的容器页，加载数据、筛选、选择实时/快照、刷新、补存和分享管理。
- `RecruitingBoardView`：纯展示共享组件，渲染上述七个区块，不承担权限、请求或链接管理。
- `DashboardKpiGrid`、`RecruitingFunnel`、`DivisionBoardGrid`、`HrbpEfficiencyGrid`、`PositionSummaryTable`：专注单一区域的小组件。
- `SharedDashboard`：匿名容器，加载 token 对应 DTO 后复用 `RecruitingBoardView`，无内部控制入口。

新组件使用页面局部样式或现有 `dashboard.css` 的命名空间，避免影响简历、岗位、面试等其他页面。

## 错误处理与性能

- 实时聚合使用固定数量的批量 SQL 查询，避免按岗位、事业部或 HRBP 的 N+1 查询。
- 快照读取仅查询一行 JSON，不重新扫描业务表。
- Cron 或手动生成失败时不生成部分数据：只有完整 DTO 序列化成功才插入快照；错误写入服务端日志与操作日志。
- 对不存在快照返回 404；已有日期手动补存返回 409；非管理员补存返回 403。
- 某个数据维度未采集不应令整页失败，DTO 返回可用性标记，前端显示 `—` / “暂未采集”。
- 无效、过期、撤销的分享链接仍统一返回 404。

## 验收标准

- 最新实时数据与任一历史快照可切换；修改实时业务数据后，历史快照数值保持不变。
- 同一日期执行两次自动/手动快照不会覆盖第一份数据。
- 内部与分享页在同一数据版本下显示相同的聚合指标；分享页不泄露候选人、联系方式、简历或 AI 原始评价。
- 实时分享随业务数据变化；快照分享不随业务数据变化。
- 页面始终显示七个区块；缺数据只影响对应数字，不影响其他区块或渲染。
- 全量岗位明细默认展开第一个事业部，支持单独折叠/展开，且合计行与当前筛选结果一致。
- Worker 聚合、快照不可变性、分享模式、权限、无数据状态和表格展开逻辑都有自动化测试。
